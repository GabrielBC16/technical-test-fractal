# MaintenanceBoard database

These scripts bootstrap SQL Server 2017 or newer. Use a separate deployment identity;
the application login must never be a database owner or a server administrator.
Open the SQL files in Visual Studio or SQL Server Management Studio. There is no SSDT project.

## Apply scripts

Create an empty application database first using an authorized deployment account.
Run scripts in this order against that database:

1. `001_schema.sql`: schemas, tables, named constraints, indexes, append-only history trigger.
2. `002_seed_status_transitions.sql`: the four allowed transitions.
3. `003_ticket_procedures.sql`: Unicode whitespace guard and four transactional write procedures.
4. `004_api_security.sql`: dedicated SQL login, database user, role, and least-privilege grants.

From the repository root, using Windows authentication for deployment:

```powershell
# Load the deployment secret into MAINTENANCEBOARD_API_PASSWORD using your secret manager.
# It is the SQL login password, not an AppUser password.
./database/Apply-Database.ps1 -Server '<sql-server-instance>' -Database '<database-name>' -UseIntegratedSecurity
```

For SQL authentication, supply deployment credentials through `SQLCMDUSER` and
`SQLCMDPASSWORD`, and omit `-UseIntegratedSecurity`. The script never puts a password
on the command line. Optional environment variables `MAINTENANCEBOARD_API_LOGIN` and
`MAINTENANCEBOARD_API_USER` default to `MaintenanceBoardApi`.

The security script takes `ApiLoginHex`, `ApiUserHex`, and `ApiPasswordHex` SQLCMD
variables supplied automatically by the PowerShell runner. They contain hexadecimal
UTF-16 encodings to make textual substitution safe. Encoding is not encryption:
do not print, commit, or retain these values in logs. The password must contain
12–128 characters and satisfy the SQL Server password policy. SQL authentication
must be enabled on the instance before connecting as the API login.

Use `-SkipSecurity` to apply only schema, transition seeds, and procedures when login
provisioning is managed separately. Azure SQL Database needs a platform-specific
contained-user provisioning script; `004_api_security.sql` targets SQL Server.

For the technical-test development setup, security provisioning may remain deferred:

```powershell
./database/Apply-Database.ps1 -Server '<sql-server-instance>' -Database '<database-name>' -UseIntegratedSecurity -SkipSecurity
```

For a local development server with a self-signed certificate, append
`-TrustServerCertificate`. This opt-in switch is also available on the concurrent
assignment test runner. Prefer a trusted certificate outside local development.

Schema and procedure scripts explicitly set the SQL session options required by
the filtered history index. Procedure definitions capture `QUOTED_IDENTIFIER ON`;
the Unicode whitespace guard uses binary collation to match .NET whitespace checks.
Reapply `001_schema.sql` and `003_ticket_procedures.sql` when updating an earlier
bootstrap, using the same deployment identity. Existing ticket data is preserved.

Reapplying the scripts preserves data, inserts missing transition seeds, replaces
procedure/trigger definitions, and reapplies grants. It does not reconcile an older
table definition, migrate a legacy `APP_USER` table, or rotate an existing login's
password. This repository currently has no legacy database migration baseline.
Schedule incompatible table changes as new numbered migrations.

## Persistence contract

- `access.AppUser` has `UserName`, `PasswordHash`, `CreatedAtUtc`, and one of the
  exact roles `Requester`, `Operator`, or `Supervisor`. The unique username index
  follows the database collation; use a case-insensitive database collation for
  case-insensitive usernames. BCrypt hashes will be generated by Infrastructure,
  not by T-SQL. No development credentials are seeded by these bootstrap scripts.
- Status values are exact, case-sensitive English identifiers: `Pending`,
  `InProgress`, `Closed`, and `Rejected`. Leading/trailing spaces are not aliases.
- Every ticket receives one initial `Created` event. The creation SP ensures it
  exists; a filtered unique index prevents a second initial event.
- History only accepts `Created`, `StatusChanged`, `Assigned`, and `Comment` events.
  Its shape constraints distinguish transitions from comments and assignments.
- Assignments store their own justification and creator. The corresponding history
  event stores the assigned user in `RelatedUserId` and the justification in `Comment`.
- Every workflow write locks the ticket first with `UPDLOCK, HOLDLOCK`. Assignment
  count, duplicate checks, and transition guards execute inside that transaction.
  Starting attention requires at least one assignee. A stale expected status fails
  before transition validation. Procedures must be invoked as standalone commands;
  their error handlers roll back the transaction, including an enclosing transaction.
- The first assignment needs no justification; the second and third do. Duplicate
  assignment takes precedence over the maximum-count error. Supervisor self-assignment
  is allowed. Assignment is restricted to open tickets.
- Cause is supplied and persisted on closure. Rejection requires a reason in the
  transition comment. Comments remain allowed on terminal tickets. Adding a comment
  or assignment does not change `Ticket.UpdatedAtUtc`; it represents creation or the
  latest status transition. Event timestamps capture other activity.
- All textual columns are `nvarchar`; all timestamps are UTC `datetime2(7)`.
  `rowversion` is an optimistic-concurrency token, not a date or time.
- Runtime actors must come from the authenticated principal. Procedure arguments
  are populated by application services, never directly from actor IDs in request bodies.
- The runtime database role can SELECT the five application tables and EXECUTE only
  the four write procedures. Direct table INSERT/UPDATE/DELETE and schema alteration
  are denied. Same-owner ownership chaining permits static SQL inside the procedures.
  The append-only trigger also rejects history updates/deletes by ordinary owner tooling;
  administrators can still change schema and must use a separate deployment identity.
- Read queries in Infrastructure must exclude `Rejected` from the main board; the
  general filtered listing may include it. History ordering is `CreatedAtUtc, HistoryId`
  so equal timestamps have a deterministic tie-breaker.

## Error contract for Application and API

| SQL error | Meaning | Application exception | HTTP |
| --- | --- | --- | --- |
| 50001 | Ticket not found | TicketNotFoundException | 404 |
| 50002 | Invalid transition or missing assignee when starting | InvalidTicketTransitionException | 409 |
| 50003 | Expected status is stale | TicketConcurrencyException | 409 |
| 50004 | Closure cause required | TicketCauseRequiredException | 422 |
| 50005 | Rejection reason required | TicketRejectionReasonRequiredException | 422 |
| 50006 | Assignment limit reached | TicketAssignmentLimitException | 409 |
| 50007 | Additional-assignment justification required | TicketAssignmentJustificationRequiredException | 422 |
| 50008 | Assignee not found, inactive, or ineligible | InvalidTicketAssigneeException | 422 |
| 50009 | Assignment duplicate or ticket not open | TicketAssignmentConflictException | 409 |
| 50010 | Actor missing or inactive | UnauthenticatedUserException | 401 |
| 50011 | Role or ownership rule denied | ForbiddenOperationException | 403 |
| 50012 | Missing/oversized input or invalid provisioning variable | RequestValidationException | 400 |
| 50013 | Empty standalone comment | TicketCommentRequiredException | 422 |
| 50014 | History update/delete attempted | ImmutableTicketHistoryException | 409 |
| 50015 | Unsafe existing database principal | Deployment-only error; not returned by application SPs | N/A |

These exception types and HTTP mappings are the contract for later implementation
milestones, not classes already implemented by this database-only milestone.

## Validation

Apply scripts twice to an isolated validation database to check repeatability, then
run `tests/001_ticket_workflow.sql` using the deployment identity and `sqlcmd -b`.
The test refuses to run unless the database name starts with `MaintenanceBoard_Validation`.
It creates validation-only users (non-BCrypt placeholder hashes that cannot be used
for application login) and durable test tickets. Never run it against application data.

```powershell
sqlcmd -S '<sql-server-instance>' -d '<MaintenanceBoard_Validation_suffix>' -E -b -i ./database/tests/001_ticket_workflow.sql
```

The workflow checks exact event counts, all required guards, requester ownership,
history immutability, and rollback after an intentionally failed history insert.
Verify actual concurrent sessions using `tests/Test-ConcurrentAssignments.ps1`.
The latter creates its own fixtures and requires the same validation database guard.

```powershell
./database/tests/Test-ConcurrentAssignments.ps1 -Server '<sql-server-instance>' -Database '<MaintenanceBoard_Validation_suffix>'
```

Static T-SQL parsing can run without a database engine using ScriptDom from Visual
Studio SQL tooling or SQL Server Management Studio:

```powershell
./database/tests/Test-SqlSyntax.ps1 -ScriptDomPath '<path-to-Microsoft.SqlServer.TransactSql.ScriptDom.dll>'
```

Syntax validation does not prove transaction behavior, permission enforcement,
idempotent execution, or concurrent correctness; run the database tests separately.
